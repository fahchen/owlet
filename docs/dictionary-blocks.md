# User-Defined Word Blocks

Status: design proposal, not implemented. The user has chosen the shape: **no local dictionary source** — a word's dictionary content is generated by the model — shown in the lookup card and in the notebook entry, with blocks defined by the user and a bulk update across saved words. Nothing below is in `spec/` yet; accepting it adds a BDR, a response contract and a settings page.

This supersedes the "local dictionary first" direction in [`spec/.discovery/dictionary-sources.md`](../spec/.discovery/dictionary-sources.md) for this round. That file stays as research: imported or system dictionaries could later join as another content source without changing the block model.

## What a block is

A block is one section of a word's entry. The user defines it; the app ships none.

| Field | Meaning |
| --- | --- |
| `id` | Stable identifier, generated once. Model responses echo it. |
| `title` | Heading shown in the card and the entry. User text, never translated. |
| `instruction` | What the model should write for this block, e.g. "Give two example sentences in the word's language, each followed by its meaning in the entry's definition language." |
| `enabled` | Disabled blocks are neither requested nor shown. |
| `order` | The order sections appear in. |

Content is plain text with line breaks; the app does not render Markdown, tables or images. An instruction that wants a list writes one item per line.

No default blocks, no preset titles. The settings empty state shows an example instruction as placeholder text only — the user composes their own. Whether the Add menu should offer insertable templates is decision 1.

## Where it shows

- **Lookup card.** After the existing meaning, one section per enabled block: title, then text. The card keeps its 320 pt width; sections are collapsible when long (decision 2). The card's existing rules stay: looking up never collects, and the card can be closed with the word.
- **Notebook entry detail.** The same sections under the entry's meaning and contexts, shown in full. Generated content is saved with the entry, so it reads offline.

Both surfaces read one result: generating in the card and then collecting carries the sections into the entry, as the meaning already does.

## When it is generated

Never automatically with an ordinary lookup.

- **A word at a time.** A "Generate Sections" entry in the card and in the entry detail sends one request with all enabled blocks for that expression.
- **Bulk update.** The notebook already selects several entries; its toolbar gains "Update Sections". The settings page can offer "Update All Saved Words". Both ask for confirmation that names the request count, run sequentially with progress and a stop control, and report failures per entry. An entry whose update fails keeps the content it had.
- **After a definition changes.** Editing a block's instruction does not rewrite saved content by itself. Sections generated from an older instruction are marked out of date with a regenerate entry; this is what bulk update clears (decision 3).

Cost is explicit: one request per expression, containing every enabled block. Bulk update over N entries is N requests. The confirmation states this; nothing generates silently.

## Request and contract

A separate request from the lookup, so a block failure can never take away the meaning:

```json
{
  "expression": "bank",
  "language": "en",
  "lemma": "bank",
  "part_of_speech": "noun",
  "meaning": "河岸；银行",
  "context": "We sat on the bank of the river.",
  "definition_language": "zh-Hans",
  "blocks": [
    {"id": "3F2A…", "instruction": "Give two example sentences…"}
  ]
}
```

The reply is one JSON object:

```json
{"blocks": [{"id": "3F2A…", "text": "1. …\n2. …"}]}
```

Validation, following the existing contract rules:

- Exactly one object, no extra keys.
- The returned ids are exactly the requested enabled ids: none missing, none duplicated, none invented; otherwise `format`.
- `text` is a string; an empty string is legal and means "nothing to say for this word" — that section is hidden rather than shown empty.
- No source or target-language check is possible: the block text is the user's own question answered. An instruction that asks for Chinese gets Chinese; the app does not guess which language a block should be in.
- One corrective round on `format`, as learning and lookup already do.
- The blocks request is independent of the lookup request: failure, cancellation or a missing model leaves the card's meaning and the entry's saved content untouched.

Block instructions are part of the system prompt; the expression, meaning and context are data, the same injection rule as today's prompts. Instructions and generated text never enter `strings/translations.json`.

Limits to fix before implementing: enabled blocks per request, instruction length, and the total instruction size, all rejected visibly rather than truncated.

## Storage

- Lookup-only results stay in the existing in-memory lookup store, as the meaning does.
- A collected word stores its sections with the entry: block id, text, the instruction fingerprint (a hash of the instruction), definition language, and when it was generated. The title is read live from settings.
- A fingerprint mismatch marks the section out of date; the stored text still shows.
- Changing the definition language or the entry's language does not silently regenerate anything (decision 4).

## Settings

A new settings page, "Word Sections" (UI naming is decision 5):

- The list of blocks: title, instruction, on/off, reorder, add, delete.
- The empty state explains the idea and shows an example instruction as a placeholder.
- "Update All Saved Words" with a confirmation naming the count.
- Deleting a block asks what happens to saved content (decision 3). No block content is ever sent anywhere; it lives in the entry and in the in-memory lookup cache.

## Decisions for the human

1. **Templates.** No insertable examples (recommended, matching "defined by the user, not preset"), or an Add menu that inserts editable templates.
2. **Card length.** Collapse long sections in the card (recommended) or let the card grow.
3. **Deleted blocks and stale content.** Keep stored text but hide it while the block is gone, and mark stale text instead of deleting it (recommended); the alternative is deleting content immediately.
4. **Language changes.** Leave existing sections as written until the user regenerates (recommended) or regenerate automatically when the definition language changes.
5. **UI name.** "Sections", "Blocks" or "Dictionary" for the settings page and the card entries; this decides the new localized strings.

## Must be measured

- What models actually produce for user-defined instructions — especially long instructions, mixed-language instructions, and instructions that conflict with the JSON-only rule.
- Token cost and latency with several blocks, and the size of a bulk update over a realistic notebook.
- Whether providers limited to `json_object` (DeepSeek) keep the block ids intact as reliably as they keep the lookup keys.
- Card readability with long plain-text sections; whether collapse is enough.
- Whether "out of date" is understandable and whether people actually run bulk update.
