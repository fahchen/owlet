# BDR-0018 · 浮窗内的手动输入

状态：已接受，已实现（2026-10-23，按评审确认的 UI/UX 方案重做）。设计记录见 [manual-input.zh-CN.md](../../../docs/manual-input.zh-CN.md)。

## 裁定

1. **原文条本身就是输入框。** 紧凑原文条是一个无边框的系统文本框，平时单行显示原文，点一下就地编辑，光标停在点击处；粘贴多行时最多长到五行。不加铅笔按钮，也不加「新文本」清空动作。
2. **读不到文字时不展开、不提示。** 读不到选区（含密码框、读取超时）时，原文条变成空的输入框并获得焦点，原因写在占位文字里（「未读到选中的文字，输入或粘贴后按 ⌘↩」），打字即消失；下方不显示提示条，也不展开空面板。工具栏已展开时同样收回为这条输入框。
3. **⌘↩ 处理当前文字。** 没有可写回的选区，或还没有结果时，⌘↩ 用框里的文字发起处理；已经开始接收结果时，⌘↩ 照旧说明要等结果完整（BDR-0017）。有选区且已有结果时仍是替换。编辑中右侧显示「⌘↩ 翻译」（或「润色」）。
4. **Esc 先结束编辑。** 原文条里有文字且正在编辑时，Esc 先结束编辑，再按一次才关闭浮窗；输入框为空时 Esc 直接关闭。
5. **「点击编辑」只提示几次。** 悬停在原文上显示 I 形光标与「点击编辑」，前三次之后不再显示。
6. **手动输入永不写回，权限失败保留紧凑提示。** 没有选区就不写回；缺少辅助功能权限仍是紧凑提示加「权限设置」，它的出路在系统设置。
7. **迟到的读取不覆盖用户输入。** 读取超时后输入框里一旦有了文字，迟到的选区结果被丢弃。

## 原因

像 Spotlight／Raycast：读不到和读到只差「框里有没有字」，同一个控件既显示原文又接受输入，不出现空面板，也没有一个看起来像报错的状态。评审中否决了「展开为空编辑器」（空的大面板读起来像错误）与「铅笔按钮」（原文条失败态已有分段控件，再加按钮更挤）。

## 影响

- BDR-0002 的例外：读不到文字不再是紧凑提示。
- `Notice.unreadable` 不再提供入口按钮，面板不再打开主窗口。
