# BDR-0011: Four interface languages, following the system by default

Status: Implemented (2026-10-11). Origin: user request to "implement i18n for the app, supporting English, Simplified and Traditional Chinese, and Japanese".

## Decision

- **Four interface languages**: 简体中文, 繁體中文, English, 日本語. The default follows the system; when the system language is none of the four, it falls back to Simplified Chinese.
- **Overridable in settings**: the settings "General" tab has "Interface Language", offering "Follow System" or one of the four, and the choice is persisted. It is written to `AppleLanguages` and takes effect **before any view is built**, so a change applies on the next launch instead of implementing a second language resolution inside the app.
- **Language names follow the interface language, except in the picker**: content languages (target language, fallback target, languages in the mapping table) show `Japanese` rather than `日本語` in the English interface. The "Interface Language" picker in settings is the only exception: it must write each language in its own name, or the user cannot read it before switching. For this the picker uses `Text(verbatim:)` to bypass the string catalog.
- **Text sent to the model is not localized**: the two default System Prompts, the prompt notes, the learning task descriptions, and the example JSON in `Owlet/ModelPrompts.json` (read through `DefaultPrompts`) do not change with the interface language. Model behavior and the contract therefore do not change with the interface language, and `spec/llm/contract.md` is unaffected.
- **The catalog is generated**: `Owlet/Localizable.xcstrings` is generated by `scripts/build-strings.py` from `strings/translations.json`. The source language is English and the English text **is the catalog key**; source code fetches strings through `L10n.shared.string("English key")`. `mise run lint` checks that the two agree, so the same text cannot be changed in one place and forgotten in the other.
- **Classification does not depend on text**: every decision like "choose the recovery entry by failure type" or "choose which comparison to show by type" now uses `ModelError.Kind`. Three places previously used localized text as an identifier, which would silently break once translated (see below).

## Consequences and costs

- New interface text must go into the translation table, or it shows in Chinese in that language; `mise run i18n` finds such gaps.
- The exception for language names and the picker is deliberate: do not change it to follow the interface language for the sake of "consistency".
- Integration tests that assert interface text would fail spuriously on machines in other languages; assertions should target structure and behavior, not wording.

## Impact

- `Owlet/Localizable.xcstrings` (new, 236 entries × 4 languages), `scripts/build-strings.py`, `scripts/check-i18n.py`.
- `Owlet/Settings/AppLanguage.swift` (new): `resolve` is a pure function covering four kinds of input: a saved choice / follow the system / an unknown value / no matching language.
- `project.yml`: `developmentLanguage: zh-Hans`; `mise.toml`: lint adds the catalog consistency check, and a new `i18n` task.
- `ModelError.Kind`: expanded from two kinds, "contract / service", to three, "contract / connection / service"; the panel and the text processing page choose the recovery entry from it.
- `DebugExchange`: carries `failureKind`; `sourceDivergence` no longer compares `failure == ModelError.sourceMismatch.message`.
- `spec/settings/decisions/BDR-0003`: the display rule for language names changes to follow the interface language.
