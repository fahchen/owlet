# BDR-0008: Looking up words while reading, triggered explicitly and never saved automatically

Status: Accepted (2026-10-07). All five areas are implemented (T48 to T51, 2026-10-11) and await final acceptance. Source: the word lookup intent discussion and a Suikou review.

Scope: the lookup card in reading contexts, offering an explanation, a reading and pronunciation. A query input field, query history, saving results to the notebook and writing back are left to step two.

## Decisions and reasons

- **⌘-click in read-only text looks up a word; a selection needs an explicit lookup.** In the floating panel, the read-only result on the text processing page, notebook details, history details and study expressions, holding ⌘ and clicking looks up the clicked word. When the system's word segmentation is not what the user wants, they correct it by selecting by hand; the toolbar "Look Up" and the context menu "Look Up Selection" use exactly the selected range. Selecting text by itself only shows the action toolbar, so reading, copying or dragging never sends a request by accident. On 2026-10-11 the user changed the fast path from a plain click to ⌘-click: a plain click is a normal system text click again, with no wait for the double-click interval. While ⌘ is held, the hovered word shows a faint selection colour and the pointer becomes a hand.
- **Clicking a study row still saves or unsaves it, and editable fields stay editable.** Study rows only look up from a selection, so dragging cannot save by accident. The source input field and the notebook's editable fields do not become read-only. Changing these existing behaviours for the sake of a single lookup gesture was rejected.
- **Explain the meaning in the current context; without a source sentence, give the general meaning and say there is no context.** The local context must cover the whole selection, the full text is not sent by default, and no source sentence is invented. Forcing a complete list of senses was rejected: reading only needs the meaning in this text. The meaning language follows [BDR-0005](../../learning/decisions/BDR-0005-definition-language.md); English explained in English is accepted, and no language picker is added.
- **The queried form is the title; the model's lemma is secondary.** The lemma is not guessed locally, and missing fields are not invented; a lemma identical to the form is not shown twice. The reading notation follows [BDR-0006](BDR-0006-on-demand-enrichment.md); an unknown reading may be empty, and whole sentences show no reading or part of speech.
- **Identical lookups are reused; an older explanation from another sentence shows its source and becomes the current sentence's explanation only after the user looks up again.** A cross-sentence candidate must have a real source context, and its form, known text language and explanation settings must be compatible. A general meaning without context is reused only for the exact same no-context lookup, never across forms by guessing a shared lemma. An identical lookup in flight is not requested twice. After a failure, reopening does not resend automatically; the user has to retry explicitly. A failed re-lookup keeps the readable old explanation and its source; a successful one updates only the result for the current conditions. Reuse is in memory only, capped in size and cleared on quit; there is no persistent query history.
- **The system voice speaks the queried form on demand; the model's reading is for reading.** Opening does not play anything. Playing again interrupts the previous audio, and closing or switching cards stops it. With no usable voice or an unknown text language, the button stays visible but disabled with the reason given, and the meaning stays usable. System TTS is not claimed to be authoritative for context-dependent pronunciations. The system dictionary's rich text was rejected because it cannot reliably provide the fields and in-context meaning this card needs. External dictionary audio was rejected because step one does not need another service dependency. No voice preference setting is added for now.
- **Only the current lookup card is shown; Esc closes the card first, then follows the panel's existing rules.** A late response must not overwrite a newer lookup or reopen a closed card. Actions on the card keep the reading selection and the panel. Keyboard and VoiceOver users must be able to find and trigger a lookup, hear its state and return to the text, without relying on hover.
- **Lookup results are for reading on the spot, but the user can explicitly save them to the notebook.** Looking up, looking up again and playing never save automatically, never overwrite notebook fields and never write back to the text or the source app. On 2026-10-11 the user asked that "a looked-up word can be added to the notebook", so the card offers an explicit `Add to Notebook` / `Saved` action that saves this result; the rules are in [BDR-0010](BDR-0010-collect-from-lookup.md). This is separate from "Fill In Missing" / "Regenerate" on the entry details, which still follow BDR-0006.

## Spec and implementation boundaries

- Behaviour is in [word-lookup.feature](../features/word-lookup.feature). The separate lookup contract and its local validation follow the existing model diagnostics and the rule that the API Key is never recorded. The response structure, the match to the query and the language tags can be validated; there is no promise that the program can prove the meaning, lemma or reading correct.
- Hover feedback uses only system feedback allowed by the design rules and does not change text layout; a selection does not also show hover. Native text hosting, gesture recognition timing, focus and accessibility must be verified before they ship; replacing the controls in all five places is not decided in advance.
- Length limits (set in T48): the query text is capped at 300 characters, above which "Look Up" is disabled with the reason given; the local context is capped at 1200 characters, above which a slice centred on the selection and fully containing it is used. The selection itself is never truncated.
- Hosting (verified natively in T48): read-only results use a read-only TextKit 1 `NSTextView`, and the selection toolbar and the card share one system `NSPopover`. When the toolbar appears, keyboard focus goes back to the text so keyboard selection extension is not interrupted; the card's popover can take keyboard focus so Tab reaches its buttons. Esc first lets the panel close the popover, then the panel.
